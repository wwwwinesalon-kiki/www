# 会費ペイと会員サイトのデータ境界

会費・顧客台帳の正本は会費ペイです。WWW は会員ログインと閲覧制御のため、Supabase Auth にログイン用メールアドレスを、`article_entitlements` に Auth の UUID・会費ペイ会員番号・閲覧期間だけを保持します。会費ペイ API トークンはサーバー内だけで使用します。

## 今回の変更

- 会費ペイの氏名を Supabase Auth メタデータへ渡さず、`profiles.kaihipay_customer_id` を新規更新しません。
- 招待先メールの重複確認は `profiles.email` ではなく、サーバー側の Supabase Auth ユーザー一覧で実施します。確認できない場合は招待を停止します。
- 会員 CSV を停止し、管理 API から会員プロフィールと申込者の連絡先・支払状態を出力しません。イベントの支払状態は WWW 側で手動編集できません。
- 予約一覧には会費ペイ会員番号だけを表示します。顧客の氏名や連絡先の確認・更新は会費ペイ上で行います。
- 新しいイベント予約ではサイト上で氏名・メール・LINE 名を入力させず、旧 DB 関数の必須列へ固定の非個人情報だけを渡します。Auth UUID と予約 ID で定員・重複申込を引き続き管理します。
- `20261022000000_profile_data_minimization.sql` は新規 Auth ユーザーのプロフィールに氏名・メールをコピーしないようにし、既存プロフィール・申込の連絡先情報を一般の認証済みロールから読めないようにします。予約の直接 RPC 呼び出しも INSERT トリガーで非個人情報に置き換えます。

## 本番適用

1. コードをデプロイし、同期処理の型検査・テスト・本番ログを確認します。
2. Supabase の対象プロジェクトを確認してから、上記 SQL を適用します。未適用の間は古い Auth トリガーが新規プロフィールにメールをコピーし続けます。
3. 支払済みテスト会員で、会費ペイ照合 → 招待 → ログイン → 当月末までの閲覧を確認します。返金・翌月未払いも別途検証します。

既存の `profiles.email/name/kaihipay_customer_id` はこの SQL では消しません。消去前に権限付与手順、バックアップ、既存アカウントとの突合せを確認してください。イベント申込テーブルには過去の氏名、メール、LINE 名、自由記述メモ、支払状態が残ります。新規予約の `name/email` 列には固定値が入り、管理画面では Auth UUID から対応する会費ペイ会員番号を表示します。履歴の保持期間と消去方法、イベント料金の会費ペイ上での受付手順を決めるまでは「顧客情報は全て会費ペイのみ」とは表明できません。
